Module 10

Notifications

In progress

Whenever something worth knowing happens — a card shared, a contact saved, a follow-up falling due — a note lands in one tidy centre and a small gold count appears on the Home bell. Every note is kept in your account rather than only on the phone, and alerts reach the lock screen even when the app is closed. Follow-up reminders now arrive this way too: a server job checks every five minutes and delivers each one at the time you chose.

Something happens → you know

Built

From the moment something happens to the moment you have seen it — the bell, the day-grouped centre, and both ways of clearing unread. Notes are kept in your account, so what you have read stays read.

02

Reaching the lock screen

Built · proven on a phone

The same note travelling further — onto the lock screen even when the app is shut. This is live: saving a note triggers a push over the air, and it has been proven arriving on a real phone with the app closed.

03

A follow-up falls due → the phone buzzes

Built

New: follow-up reminders reach you at the time you chose. A server job checks for due reminders every five minutes and the phone buzzes even with the app closed. Each reminder announces exactly once — snoozing moves the time and it announces again when the new time comes — and tapping the alert opens the person it is about.

T

What powers this module

Feature by feature — what each moving part actually runs on.

  • Notification centreReact Native SectionList grouped Today / Yesterday / date · hairline separators and unread marks per row · optimistic mark-read on tap + "Mark all read" header action — TanStack Query mutations that reconcile the list and unread-count caches together, with rollback on error
  • Home bell badgeGold unread count on the Home TopBar · fed by a TanStack Query unread key over the same store · refetches on every screen focus, so returning from the centre or an emit from any flow updates it without a manual refresh
  • Writing an entrynotify() helper — the one-line way for any feature (cards, contacts, account) to drop an entry, now inserted straight into the cloud table; fire-and-forget, it never throws into the calling flow
  • Where notifications liveLive on Supabase — the PostgreSQL notifications table from migration 0004, applied and verified on 27 July · supabaseNotificationRepository is the active data layer · row-level security is on, so an account can only ever read its own notes, proven with two signed-in test sessions
  • Lock-screen deliveryFirebase Cloud Messaging on Android · a database trigger raises the send the moment a note is written, so the alert arrives with the app closed — proven on a real phone · iPhone delivery waits on the APNs key that comes with the paid Apple developer account
  • Follow-up reminder pushesA pg_cron job inside Supabase sweeps the reminders table (migration 0011, applied and verified) every five minutes and sends a reminder.due push through Firebase Cloud Messaging — the 'reminder' notification type finally has a real writer · each reminder announces exactly once, and snoozing re-announces at the new time · tapping the notification opens that contact · row-level security keeps every read and write owner-only
  • Staying signed inSupabase Auth session · the single-device sign-in lock is now active, so notes follow the one device a person is signed in on
